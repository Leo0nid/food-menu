# Состояние функций и план работ

Дата аудита: 15 сентября 2026 года.

Основание для аудита: `AGENTS.md`, `docs/product.md` и текущий код в `app/` и `server/`.

## Как определён статус

- **Реализовано** — необходимая цепочка присутствует в коде и при статическом просмотре выглядит связной. Это не означает, что функция проверена в браузере или с реальной MySQL.
- **Частично реализовано** — часть цепочки есть, но пользователь не может завершить весь сценарий либо отсутствуют безопасность, обработка результата или согласованный контракт.
- **Отсутствует** — рабочего сценария и его API/UI в текущем коде нет.

Ни один сквозной MVP-сценарий пока не подтверждён автоматическим или ручным E2E-тестом.

## Реализованные части

### Получение активного меню по токену стола

- `GET /api/tables/:token` принимает токен, на сервере находит активный стол и определяет его ресторан.
- Меню выбирается по найденному `restaurantId`; клиент не передаёт ресторан отдельно.
- В ответ попадают только активные блюда, отсортированные по `sort_order`.
- На клиенте есть состояния загрузки, ошибки и пустого меню.

Проверено: прослежена цепочка page → composable → API → use case → repositories → mappers; все Vue SFC проходят синтаксический разбор. Не проверено: настоящий HTTP-запрос, соединение с MySQL и отображение в браузере.

### Локальная корзина

- Добавление блюда, увеличение и уменьшение количества, удаление позиции.
- Автоматическое удаление позиции при уменьшении количества до нуля.
- Расчёт общего количества товаров и общей суммы.
- Отображение счётчика в меню и элементов корзины на отдельной странице.

Проверено: статически проверены store и использующие его компоненты; Vue SFC синтаксически корректны. Не проверено: взаимодействие в браузере, переходы между столами и поведение после перезагрузки.

### Серверная запись заказа

- `POST /api/orders` валидирует базовую форму тела через Zod.
- Сервер повторно находит стол и активные блюда по собственным данным.
- Цена и итог рассчитываются на сервере; цена от клиента не принимается.
- Название и цена блюда сохраняются в снимке позиции заказа.
- Заказ и его позиции записываются внутри MySQL-транзакции с `commit`/`rollback`.

Проверено: статически прослежена цепочка API → DTO → use case → transaction → repositories. Не проверено: успешная и ошибочная запись в живую БД, откат транзакции и конкурентные запросы.

### Чтение заказов

- `GET /api/orders/:id` получает заказ с позициями.
- `GET /api/restaurants/:restaurantId/orders` получает заказы ресторана и группирует позиции по заказам.

Проверено: статически проверены SQL-запросы, мапперы и сборка ответа. Не проверено: ответы живого API. Эти маршруты пока нельзя считать готовыми для выпуска, потому что у них нет контроля доступа.

### Отображение заказов по статусам

- Админская страница получает список заказов ресторана.
- Доска делит их на четыре столбца: `new`, `cooking`, `ready`, `done`.
- Карточка показывает состав, количество, комментарий, сумму и время с момента создания заказа («7 минут назад»); время обновляется каждые 30 секунд.
- Есть загрузка, ошибка с повторным запросом и ручное обновление списка.

Проверено: все связанные Vue SFC проходят синтаксический разбор. Не проверено: загрузка данных и внешний вид в браузере. Кнопка принятия заказа пока не выполняет действие.

## Частично реализованные функции

### Вход гостя и просмотр меню

- В продукте указан маршрут `/table/:token`, а в коде используется `/menu/:token`.
- Главная страница жёстко перенаправляет на демонстрационный токен `demo-table-1`.
- Блюда выводятся без категорий, хотя категории входят в MVP.
- Не определено отдельное поведение для неверного токена и отключённого стола: сейчас оба случая сводятся к общей ошибке.

### Жизненный цикл корзины

- Корзина хранится только в памяти Pinia и исчезает после перезагрузки.
- Корзина не привязана к токену стола. При переходе между столами в ней могут остаться блюда предыдущего стола.
- Не реализована очистка после отправки заказа; требуемый момент очистки ещё не выбран продуктово.

### Оформление заказа на клиенте

- Страница корзины вызывает `POST /api/orders` и блокирует кнопку на время запроса.
- Успех и ошибка выводятся только в консоль.
- Нет пользовательского сообщения об ошибке, экрана успешного заказа, перехода к заказу и очистки корзины.
- Нет защиты от повторного создания заказа при повторе запроса после сетевой ошибки.

### Просмотр статуса заказа гостем

- Сервер умеет вернуть заказ по ID.
- Нет клиентского экрана статуса, сохранения ссылки на заказ и безопасного подтверждения, что заказ принадлежит этому гостю или столу.
- Не определено восстановление статуса после перезагрузки страницы.

### Работа администратора с заказами

- Список и визуальная группировка готовы только для чтения.
- Вместо понятного названия стола показывается часть технического UUID.
- Смена статуса отсутствует; кнопка «Принять заказ» не подключена.
- Новые заказы появляются только после ручного обновления страницы.
- Страница и API доступны по произвольному `restaurantId` без аутентификации и проверки прав.

### MySQL и структура данных

- Есть Docker Compose для MySQL, пул соединений и создание основных таблиц.
- Нет миграций и версионирования схемы; `CREATE TABLE IF NOT EXISTS` не обновит существующую таблицу при изменении структуры.
- Инициализация БД запускается асинхронно при импорте и не блокирует первый запрос, поэтому возможна гонка при старте.
- В конфигурации есть небезопасные значения подключения по умолчанию, нет `.env.example`, healthcheck и проектной инструкции запуска.
- Удаление блюда каскадно удаляет связанные исторические позиции заказа, несмотря на сохранённые снимки названия и цены.
- Статус заказа хранится как свободная строка без ограничения на допустимые значения.

### Валидация входных данных

- Zod проверяет наличие массива, целое количество не меньше одного и строковые идентификаторы.
- Не ограничены длины токена и комментария, пустые строки и максимальное количество позиций/единиц.
- Параметры GET-маршрутов проверяются вручную и непоследовательно.

## Отсутствующие функции

- Аутентификация администратора, роли и привязка администратора к ресторану.
- Создание и редактирование ресторана.
- Создание, переименование и отключение столов.
- Получение постоянной ссылки стола и генерация/скачивание QR-кода.
- Категории меню и отображение блюд по категориям.
- Управление меню: создание, редактирование, отключение, сортировка и назначение категории.
- API и UI для смены статуса заказа.
- Экран успешного заказа и гостевой экран текущего статуса.
- Безопасный способ повторно открыть свой заказ после перезагрузки.
- Идемпотентность создания заказа и защита от дублей.
- Автоматическое получение новых заказов и обновлений статусов.
- Завершение сессии гостя на ресторанном планшете.
- Автоматические unit-, integration- и E2E-тесты.
- Проектная инструкция по настройке `.env`, запуску MySQL, миграциям и проверке приложения.

Бронирование столов не включено в текущий MVP и не считается отсутствующей функцией до отдельного расширения продуктового объёма.

## Порядок выполнения оставшихся задач

Тесты для каждой задачи нужно писать и выполнять вместе с реализацией, а не откладывать все проверки на последний этап.

### 1. Зафиксировать блокирующие продуктовые решения

Зависимости: нет.

Критерии готовности:

- В `docs/product.md` записаны решения из раздела «Требует продуктового решения» ниже.
- Для статусов определены допустимые переходы и действие каждой админской кнопки.
- Определены правила гостевой сессии, повторной отправки и изменения меню во время оформления.
- Ясно разделены MVP и будущие функции.

### 2. Сделать воспроизводимыми конфигурацию и схему БД

Зависимости: решения о категориях, статусах и хранении истории заказа.

Критерии готовности:

- Добавлен `.env.example` без секретов, а README описывает локальный запуск на заявленном порту.
- Подключение к БД проверяется до приёма HTTP-запросов; ошибка старта понятна разработчику.
- Схема изменяется последовательными миграциями и поднимается с нуля на пустой MySQL.
- Повторный запуск миграций безопасен.
- Удаление блюда не уничтожает историю существующих заказов.
- Ограничения БД соответствуют согласованным статусам и категориям.
- Integration-тест подтверждает создание схемы и основные связи.

### 3. Согласовать гостевой URL и контракт меню

Зависимости: задача 1; категории также зависят от задачи 2.

Критерии готовности:

- Основным маршрутом становится согласованный `/table/:token` либо `docs/product.md` явно меняется на `/menu/:token`.
- Удалено жёсткое production-перенаправление на демонстрационный стол; demo-вход, если нужен, явно отделён.
- API и UI возвращают и отображают категории в согласованном порядке.
- Для неверного и отключённого токена реализованы согласованные состояния.
- Integration-тесты покрывают активный стол, отключённый стол, неверный токен и пустое меню.
- Сценарий вручную проверен на телефоне и планшете.

### 4. Привязать корзину к столу и определить её хранение

Зависимости: задачи 1 и 3.

Критерии готовности:

- В корзине хранится токен или идентификатор текущего стола.
- При открытии другого стола выполняется согласованное действие: очистка либо явное подтверждение переноса.
- Поведение после перезагрузки соответствует продуктовому решению.
- Добавление, увеличение, уменьшение до нуля, удаление, количество и сумма покрыты unit-тестами.
- В браузере проверены пустая корзина, несколько блюд и повторное добавление одного блюда.

### 5. Усилить создание заказа

Зависимости: задачи 1, 2 и 4.

Критерии готовности:

- Zod ограничивает пустые строки, длину комментария, число позиций и количество единиц.
- Дубликаты `menuItemId` в одном запросе запрещаются или объединяются по зафиксированному правилу.
- Сервер применяет согласованное правило при изменении цены или доступности блюда.
- Повтор одного логического запроса с idempotency key не создаёт второй заказ.
- Integration-тесты подтверждают серверный расчёт цены, откат всей транзакции при ошибке и отсутствие дублей.
- Клиент различает ошибки валидации, недоступный стол/товар и временную ошибку сервера.

### 6. Завершить гостевой сценарий оформления

Зависимости: задача 5 и решение о жизненном цикле корзины.

Критерии готовности:

- Ошибка отправки видна на странице и допускает безопасный повтор.
- После успеха открывается экран с номером/идентификатором заказа, суммой и начальным статусом.
- Корзина очищается в согласованный момент, но не теряется при неуспешном запросе.
- Повторный клик и обновление страницы не создают дубликат.
- E2E-тест проходит путь: открыть стол → добавить блюда → изменить количество → добавить комментарий → оформить заказ.

### 7. Добавить аутентификацию и авторизацию администратора

Зависимости: продуктовое решение о модели доступа.

Критерии готовности:

- Есть вход и выход администратора, безопасная сессия и выбранный способ восстановления доступа.
- Все маршруты `/api/restaurants/:restaurantId/**` проверяют сессию и право на конкретный ресторан.
- Пользователь одного ресторана не может читать или менять данные другого.
- Невошедший пользователь получает `401`, а пользователь без права — `403`.
- Это подтверждено integration-тестами, а не только скрытием страниц во фронтенде.

### 8. Завершить административную обработку заказов

Зависимости: задача 7 и решение о переходах статусов.

Критерии готовности:

- API смены статуса проверяет текущий статус, допустимый переход и права администратора.
- Карточка показывает понятное имя/номер стола, а не часть UUID.
- Для каждого столбца доступно только допустимое следующее действие.
- После действия карточка переходит в правильный столбец и показывает ошибку при конфликте.
- Новые заказы и изменения появляются автоматически выбранным способом: polling, SSE или WebSocket.
- Integration- и UI-тесты покрывают все разрешённые и запрещённые переходы.

### 9. Реализовать безопасный гостевой статус заказа

Зависимости: задачи 1, 5 и 8.

Критерии готовности:

- Ответ создания заказа выдаёт непрогнозируемый гостевой ключ/ссылку либо создаёт согласованную сессию.
- Нельзя получить чужой заказ только по публичному ID.
- Страница показывает текущий статус и автоматически получает обновления.
- После перезагрузки гость возвращается к своему заказу согласно продуктовому решению.
- E2E-тест подтверждает переход заказа по всем статусам от гостя до завершения.

### 10. Реализовать управление рестораном

Зависимости: задачи 2 и 7.

Критерии готовности:

- Авторизованный администратор может создать и изменить разрешённые данные своего ресторана.
- Slug и другие уникальные поля валидируются с понятными ошибками.
- Нельзя управлять чужим рестораном.
- Есть integration-тесты успешных операций и отказов доступа.

### 11. Реализовать управление столами, ссылками и QR

Зависимости: задачи 3, 7 и 10; решение о выключенном столе.

Критерии готовности:

- Администратор может создать, переименовать и отключить стол.
- Токен непредсказуем, уникален и не совпадает с внутренним ID.
- Для стола показывается постоянная гостевая ссылка и генерируется скачиваемый QR-код с этой ссылкой.
- Отключённый стол обрабатывается по согласованным правилам для новых и уже открытых сессий.
- Integration- и E2E-тесты покрывают создание стола, открытие ссылки и отключение.

### 12. Реализовать управление категориями и меню

Зависимости: задачи 2, 7 и 10; решение о составе операций меню.

Критерии готовности:

- Администратор может выполнять согласованный набор операций с категориями и блюдами.
- Цена хранится целым числом копеек и валидируется как неотрицательная в допустимом диапазоне.
- Сортировка категорий и блюд стабильна.
- Отключённое блюдо исчезает из новых меню, не разрушая историю заказов.
- Изменения одного ресторана недоступны другому.
- Integration- и E2E-тесты покрывают CRUD/отключение и отображение результата в гостевом меню.

### 13. Завершить сценарий ресторанного планшета

Зависимости: задачи 3, 4, 6, 9 и 11.

Критерии готовности:

- Та же гостевая ссылка корректно работает на закреплённом планшете без отдельной версии приложения.
- Есть согласованный и реализованный способ завершить заказ/сессию и подготовить планшет для следующего гостя.
- Данные предыдущего гостя не видны следующему.
- Сценарий проверен вручную на планшетном размере и E2E-тестом смены двух последовательных гостей.

### 14. Выполнить итоговую проверку MVP и обновить документацию

Зависимости: все включённые в MVP задачи выше.

Критерии готовности:

- Выполняются typecheck, lint, unit-, integration- и E2E-тесты отдельными командами.
- Production build проходит с чистого checkout.
- Пройдены все сценарии проверки из `docs/product.md` на чистой БД.
- README описывает установку, `.env`, MySQL/Docker, миграции, seed/demo-данные, запуск и тесты.
- Проверены мобильный, планшетный и десктопный интерфейсы.
- В документации не осталось незафиксированных блокирующих решений.

## Требует продуктового решения

1. Как администратор входит в систему, какие роли существуют и может ли один пользователь управлять несколькими ресторанами.
2. Какие статусы заказа входят в MVP, какие переходы допустимы и требуется ли отдельное подтверждение принятия.
3. Когда очищать корзину: сразу после создания заказа или после его завершения.
4. Как гость повторно открывает свой заказ и видит статус после перезагрузки, не получая доступ к чужим заказам.
5. Как завершается сессия на ресторанном планшете и начинается сессия следующего гостя.
6. Какие операции управления меню входят в MVP и обязательны ли категории, изображения, остатки и модификаторы блюда.
7. Что видит гость при неверном/отключённом столе и что происходит с уже собранной корзиной или созданным заказом.
8. Что делать, если цена или доступность блюда изменилась между открытием меню и отправкой заказа.
9. Какой UX использовать при таймауте и повторной отправке; сколько времени действует ключ идемпотентности.
